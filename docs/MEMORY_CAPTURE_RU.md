# Автоматический захват важного в память — анализ и предложение

Статус: **предложение**. Вопрос: как ArchitectOS должен решать, что из диалога
(Ask, MCP-агент, хуки Cursor / Claude Code / Codex) стоит сохранить в память, и
как дать пользователю переключатель «сохранять автоматически, как Claude» /
«тот же отбор, но с ручным принятием кандидатов».

Что ниже сказано про Claude, взято из публичной документации Claude Code
(`code.claude.com/docs/en/memory`, раздел Auto memory) и справки Claude.ai
(«Memory and context management»). Внутренний промпт и пороги Anthropic не
опубликованы; там, где я их домысливаю, стоит пометка «предположение».

---

## 1. Как это делает Claude

### 1.1. Claude Code — auto memory

| Аспект | Как устроено |
| --- | --- |
| **Кто решает** | Сама модель во время работы. Отдельного классификатора нет: Claude сам пишет файлы в `~/.claude/projects/<project>/memory/` обычными файловыми инструментами. |
| **Критерий** | Документация формулирует один: *«решает, что стоит запомнить, исходя из того, пригодится ли информация в будущем разговоре»*. Сохраняет не каждую сессию. |
| **Четыре вида заметок** (`type` во frontmatter) | `user` — роль, экспертиза, рабочие предпочтения; `feedback` — исправления пользователя и подтверждённые подходы; `project` — текущая работа, сроки, решения, которые **нельзя вывести из кода или git**; `reference` — где искать информацию вне проекта (трекер, дашборд). |
| **Что не сохраняет** | Всё, что выводится из кодовой базы (архитектура, пути файлов, найденные фиксы); всё, что уже сказано в CLAUDE.md. |
| **Явный триггер** | «Запомни: …» → в auto memory; «добавь в CLAUDE.md» → в инструкции. |
| **Подтверждение** | Нет. Запись сразу, пользователь видит «Saved 2 memories» и может открыть/отредактировать/удалить файлы (`/memory`). |
| **Структура** | `MEMORY.md` — индекс, одна строка на память; загружается в каждую сессию, но **только первые 200 строк / 25 КБ**. Детали — в отдельных topic-файлах, читаются по требованию. При приближении к лимиту Claude получает напоминание ужать индекс; при превышении — ошибку. |
| **Свежесть** | При записи Claude Code проставляет `modified` (ISO-время) во frontmatter, чтобы и человек, и модель видели, насколько факт актуален. |
| **Область** | На репозиторий (все worktree делят одну директорию), локально на машине. Субагенты — своя память. |
| **Выключение** | `/memory` → toggle (`autoMemoryEnabled`), per-project в settings, `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`. |

**Предположение** о том, как модель принимает решение (из поведения и формулировок
документации): в системный промпт встроены описание четырёх видов и критерий
«полезно ли в будущем», а сигналами служат исправления («нет, делай так»),
явные предпочтения, подтверждения («да, так и оставь»), факты о контексте, которых
нет в репозитории. Это оценка *полезности и невыводимости*, а не поиск ключевых
слов.

### 1.2. Claude.ai (чат)

- Память **автоматическая**: Claude сохраняет «набор отдельных тем по ходу чата»,
  а не пересказ после. Явное «запомни» тоже работает.
- Категории: роль/проекты/профессиональный контекст; люди и места; стиль общения;
  технические предпочтения; детали проектов.
- Исключения по умолчанию: чувствительные темы (здоровье, политика, религия) —
  только по opt-in; часть данных (номера документов, счета) не сохраняется никогда.
- Пользователь видит темы в Settings → Your memory, правит, удаляет, ставит на
  паузу или сбрасывает. Память проекта изолирована от других проектов.

### 1.3. Общие принципы подхода Claude

1. Решение принимает **модель**, по смыслу, с явным списком видов и критерием
   полезности, а не регулярками.
2. **Негативные критерии** важнее позитивных: не сохранять выводимое из кода и
   уже записанное — именно это держит память маленькой.
3. **Нет очереди на подтверждение**; вместо неё — прозрачность («Saved N
   memories»), редактируемый plain-text и лёгкое удаление.
4. **Бюджет на то, что загружается** (200 строк индекса), детали — по требованию.
5. Память **типизирована** (`user/feedback/project/reference`) и датирована.

## 2. Как это сделано в ArchitectOS сейчас

Путь: `evaluate_chat_turn` (`chat_memory.py`) → `extract_durable_facts` →
`_enqueue_session_fact_atoms` (`chat_session_service.py`) → очередь кандидатов →
`_maybe_auto_accept_chat_candidate` → `promote_memory_candidate`. Тот же путь у MCP
`memory_turn` и хуков (`capture_memory_turn`). Поверх всего — шлюз дедупликации
(`MEMORY_DEDUP_RU.md`).

| Аспект | Как устроено |
| --- | --- |
| **Кто решает** | Детерминированные эвристики без LLM: список стоп-фраз (приветствия), ~40 regex «долговечных» сигналов RU/EN (`decision`, `must`, `never`, `нельзя`, `баг`, `api`, `schema`…), длина сообщения, маркеры списков в ответе. |
| **Критерий** | `chat_turn_score` 0..1: +0.45 за сигнал у пользователя, +0.25 у ассистента, +0.15/+0.1 за длину, +0.1 за must/never. Режимы: `off` / `strict` (порог 0.45 или извлечённые факты) / `aggressive` (порог 0.25 или длина ≥ 100). |
| **Что извлекается** | Строки пользователя с сигналом; буллеты и фразы вида «decision: …» из ответа; fallback — склейка «user → assistant» (strict) или блоб «User: … Assistant: …» (aggressive). Тип факта — по ключевым словам: Decision / Requirement / Constraint / Lesson; отдельный «Rule»-кандидат от `_capture_rules_candidate`. |
| **Подтверждение** | Очередь кандидатов с TTL 7 дней. Авто-принятие (`chat_auto_accept`, по умолчанию вкл., **в UI не показано**) только для `Lesson` с confidence ≥ 0.70, без дубля и без ревизии. Decision / Constraint / Requirement — всегда ручное принятие. |
| **Когда** | Ask: атомы при завершении сессии (End session / простой 30 мин), сводка сессии строится теми же эвристиками в режиме aggressive; плюс rules-keeper после каждого «долговечного» хода. MCP/хуки: на каждом ходе. |
| **Что не сохраняет** | Приветствия, короткие реплики, секреты (редакция). Критерия «выводимо из кода» и «уже есть в документации» **нет**. |
| **Структура/бюджет** | Узлы графа с типом, scope, lifecycle-тиром, `created_at`. Бюджет есть на стороне чтения (Context Builder, briefing), не на стороне записи. |
| **Прозрачность** | Keeper-события, Review Queue, вкладка «Дубликаты», события `dedup` с отменой. |

### 2.1. Где подход ArchitectOS слабее

1. **Ключевые слова вместо смысла.** «Используй pnpm, а не npm» не содержит ни
   одного слова из `_DURABLE_PATTERNS` → в strict-режиме факт потеряется (длина
   < 60). А «я исправил баг в api» содержит `баг` и `api` → сохранится, хотя это
   выводимо из git. Ложные срабатывания и пропуски симметричны.
2. **Нет категории «исправление» (feedback).** Самый ценный сигнал у Claude —
   «нет, не так», «вместо X делай Y», «да, так и оставь» — у нас не распознаётся
   вовсе: ни одного паттерна отрицания-коррекции в списке нет.
3. **Нет негативных критериев.** Архитектура, пути файлов, детали фикса, то, что
   уже лежит в `docs/` или в памяти, — всё это проходит отбор наравне с решениями.
   Это главный источник шума в Review Queue (и причина, по которой понадобился
   этап дедупликации).
4. **Типы не те.** Decision / Constraint / Requirement / Lesson описывают *проектные
   факты*; у Claude половина пользы — в `user` (как человек любит работать) и
   `feedback` (что он поправил). У нас для этого нет ни типа, ни scope: такие
   факты либо падают в `Lesson` проекта, либо теряются.
5. **Авто-принятие по типу, а не по риску.** `Lesson` принимается автоматически,
   `Constraint` — никогда. Но `Lesson` из aggressive-блоба «User: … Assistant: …»
   рискованнее, чем «Constraint: не коммитить в main», сказанный пользователем
   прямо.
6. **Переключатель спрятан и неочевиден.** В UI есть `off / strict / aggressive`
   (это про *сколько* отбирать), а `chat_auto_accept` (это про *спрашивать ли*)
   в настройках нет. Пользователь не может выбрать «отбирай как Claude, но
   спрашивай».
7. **Нет бюджета на записи и индекса.** Память растёт неограниченно; «что Claude
   увидит в начале сессии» определяется ретривером, а не осознанным списком
   из N строк. Это не дефект, а другая модель (у нас поиск, у Claude индекс), но
   без лимита shortlist-а нет сигнала «память раздулась».

### 2.2. Где ArchitectOS сильнее — и это надо сохранить

- **Очередь на ревью** с TTL — у Claude её нет, а для командной/проектной памяти
  она нужна: решение, попавшее в общую память по ошибке, дороже личной заметки.
- **Дедупликация, ревизии и конфликты** на входе (`SUPERSEDES`, `CONTRADICTS`,
  отмена) — у Claude дубли и противоречия живут в markdown, пока он сам не
  заметит.
- **Один движок для трёх транспортов** (UI, MCP, хуки) и per-turn инъекция.
- **Работает без LLM** и без сети, детерминированно, с тестами.
- **Lifecycle** (short/long-term, decay, архив) вместо «всё навсегда».

## 3. Предложение

Идея: **алгоритм отбора один и тот же, а переключатель меняет только то, что
происходит с результатом** — пишется сразу или ждёт принятия. Это и есть
запрошенные два режима; третий — выключено.

### 3.1. Политика захвата `memory_capture`

Новая настройка (заменяет `chat_memory_mode` + скрытый `chat_auto_accept`):

```jsonc
{
  "mode": "review",            // auto | review | off
  "extractor": "auto",         // auto = LLM если настроен провайдер, иначе heuristic; heuristic; llm
  "auto_kinds": ["user", "feedback", "reference", "project"],   // что в mode=auto пишется сразу
  "always_review": ["conflict", "update", "secret_adjacent"],   // что в любом режиме ждёт человека
  "min_confidence": 0.7,       // ниже — в ревью даже в auto
  "aggressiveness": "normal",  // conservative | normal | eager — порог отбора, не судьба записи
  "budget_index_lines": 200    // размер «стартового индекса» (§3.5)
}
```

| `mode` | Поведение |
| --- | --- |
| **`auto` — «как Claude»** | Извлечённые факты с confidence ≥ порога пишутся сразу через шлюз дедупликации; пользователь видит «Сохранено N фактов» и может отменить одним кликом (события `dedup`/`created` уже есть). В ревью остаются только конфликты, обновления значений (`SUPERSEDES`) и факты с низкой уверенностью. |
| **`review` — «как Claude, но вручную»** | Тот же экстрактор, те же категории и confidence, но **всё** становится кандидатом в Review Queue с TTL. Карточка показывает вид (`feedback`/`user`/…), уверенность и цитату-основание, чтобы принимать быстро. |
| **`off`** | Только явное «Запомни»/★ и MCP `memory_add`. |

Миграция текущих значений: `off → off`; `strict → review`;
`aggressive → review` с `aggressiveness: eager`; `chat_auto_accept: true` при
`strict` → `auto` с `auto_kinds: ["feedback", "user", "reference"]` (то, что
сейчас фактически авто-принимается как `Lesson`, станет этими видами).

### 3.2. Экстрактор: два яруса

**Ярус 1 — детерминированный предфильтр** (есть, бесплатный, без сети):
`is_chitchat_user_message`, редакция секретов, длина. Отсекает ~80% ходов до
того, как они дойдут до чего-то дорогого. Сюда добавить сигналы **исправлений**
(которых сейчас нет): `нет, не так`, `не надо`, `вместо`, `больше не`, `всегда
делай`, `don't`, `instead`, `stop doing`, `actually`, повтор инструкции после
ответа ассистента.

**Ярус 2 — LLM-экстрактор** (новое; включается, если настроен провайдер, иначе
работает нынешняя эвристика). Один вызов на ход (MCP/хуки) или на сессию (Ask),
роль `review`/дешёвая модель через существующий роутер. Промпт воспроизводит
логику Claude:

> Из этого обмена выдели факты, которые пригодятся в **будущем** разговоре об
> этом проекте. Виды: `user` (роль, предпочтения, стиль работы человека),
> `feedback` (исправление или явное подтверждение подхода), `project` (решение,
> ограничение, срок, статус работы, которые **нельзя вывести из кода, git или
> документации**), `reference` (где искать информацию вне репозитория).
> **Не выделяй**: архитектуру, пути, содержимое кода, детали отладки, то, что
> уже есть в «Известно» ниже, секреты, временные детали текущей задачи,
> приветствия. Для каждого факта: `kind`, `type`
> (Decision/Constraint/Requirement/Lesson/Preference), `text` (одно предложение,
> без местоимений), `confidence` 0..1, `evidence` (точная цитата), `subject`
> (путь/символ, если есть). Если ничего нет — пустой список.

Блок «Известно» — это top-k из `memory_dedup` preview + briefing по проекту:
так негативный критерий «уже записано» выполняется до записи, а не после.
Структурированный ответ парсится как в `_parse_dedup_verdict`; мусор → fallback
на эвристику.

Защита от самоподтверждения: LLM-экстрактор не видит тексты, которые уже
отредактированы по секретам; его вывод проходит ту же редакцию ещё раз.

### 3.3. Что считается «важным» — критерии в одном месте

Перенести из разрозненных regex в явную таблицу `memory_capture.py`, чтобы оба
яруса и подсказка в UI читали одно и то же:

| Сохранять | Не сохранять |
| --- | --- |
| исправление или подтверждение от пользователя | то, что выводится из кода/git/тестов |
| предпочтение по инструментам, стилю, процессу | то, что уже есть в памяти/CLAUDE.md/docs (проверка через dedup preview) |
| решение с обоснованием, принятое в диалоге | детали текущей задачи, которые устареют к концу дня |
| ограничение/правило («никогда…», «только…») | секреты, токены, персональные данные |
| внешняя ссылка/место, где искать (трекер, дашборд, канал) | приветствия, благодарности, подтверждения «ок» |
| срок, статус, договорённость с людьми | пересказ ответа ассистента без новой информации |

### 3.4. Виды и типы

Добавить к узлу `metadata.kind ∈ {user, feedback, project, reference}` и новый
`type = Preference` (для `user`-фактов). `user`-факты по умолчанию получают
scope `global` (они про человека, а не про проект), остальные — `project`.
Вид определяет **риск**, а значит — авто-запись: `feedback` и `user` безопасны
(ошибка стоит одной отменённой заметки), `project`-Decision влияет на команду →
в `auto` пишется только при confidence ≥ 0.85, иначе в ревью.

### 3.5. Бюджет и прозрачность (из подхода Claude)

- **Стартовый индекс**: briefing-пак уже существует; добавить ему лимит
  `budget_index_lines` (200) и предупреждение в UI «индекс памяти превысил
  бюджет — N фактов не попадут в старт сессии», с кнопкой перехода к компактизации
  (`MEMORY_DEDUP_RU.md`, §5). Это аналог напоминания Claude Code «ужми MEMORY.md».
- **«Сохранено N фактов»**: тост в Ask и строка в Agent activity после каждого
  авто-сохранения, с «Отменить» (переиспользует `undo_memory_dedup` и событие
  `created`).
- **`modified`/свежесть**: уже есть `updated_at`; показывать его в карточке и в
  briefing-строке, как делает Claude Code с frontmatter.
- **Явное «Запомни:»** в Ask и через хуки — всегда прямая запись, в любом режиме
  кроме `off` (как у Claude), с `kind` по содержимому.

### 3.6. UI настроек

Страница «Память чата» → «Захват памяти»:

```
Как сохранять важное из диалогов
 (•) Автоматически — как Claude. Факты пишутся сразу; конфликты и спорное — в ревью.
 ( ) Через ревью — тот же отбор, но каждый факт ждёт вашего принятия.
 ( ) Выключено — только «Запомни» и ★.

Что отбирать:  [консервативно | обычно | побольше]
Экстрактор:    [авто: LLM, если есть провайдер ▾]   ⓘ один вызов дешёвой модели на ход
Дополнительно ▾
  [x] Исправления и предпочтения (user, feedback) — сразу
  [x] Ссылки и места (reference) — сразу
  [ ] Решения проекта (project) — сразу при уверенности ≥ 0.85
  Порог уверенности: 0.70
```

Под переключателем — живой счётчик: «за 7 дней: сохранено 23, в ревью 9,
отменено 1», чтобы режим можно было выбирать по факту, а не вслепую.

## 4. План внедрения

| Этап | Объём | Результат |
| --- | --- | --- |
| **A. Политика и переключатель** | `memory_capture` в настройках + миграция из `chat_memory_mode`/`chat_auto_accept`; `mode` решает судьбу кандидата в `_enqueue_session_fact_atoms`/`capture_memory_turn`; UI-страница; тост «Сохранено N» с отменой | Пользователь выбирает auto/review/off; поведение экстрактора не меняется |
| **B. Критерии и виды** | `memory_capture.py` с таблицей §3.3, сигналы исправлений, `kind` + `Preference`, риск-зависимое авто-принятие; карточка кандидата показывает kind/уверенность/цитату | Ловятся исправления и предпочтения; меньше «выводимого из кода» |
| **C. LLM-экстрактор** | промпт §3.2, блок «Известно» из dedup preview, парсер, fallback, настройка `extractor`; счётчики качества (принято/отклонено по видам) | Отбор по смыслу, как у Claude, при наличии провайдера |
| **D. Бюджет индекса** | лимит briefing-строк, предупреждение, связь с компактизацией | Сигнал «память раздулась» и путь её ужать |

A и B не требуют LLM и могут идти первым PR. C — отдельный, с измерением на
реальной базе (доля принятых в review-режиме — прямой показатель точности
экстрактора: если в `review` пользователь принимает > 90% предложенного, режим
`auto` безопасен).

## 5. Риски и открытые вопросы

- **Стоимость LLM-экстрактора**: один вызов на каждый ход агента через хуки —
  это много. Смягчение: ярус 1 отсекает большинство ходов; для хуков — вызывать
  экстрактор на `Stop` (конец хода), а не на `UserPromptSubmit`; батчить ходы
  Ask до конца сессии (так уже сделано).
- **`auto` для командной памяти**: личные заметки Claude ошибаются дёшево, общая
  память проекта — нет. Поэтому по умолчанию предлагаю `review`, а `auto`
  включать осознанно; `project`-решения даже в `auto` держать за порогом 0.85.
- **Scope `global` для `user`-фактов**: сейчас `global` разделяется всеми
  проектами одной установки; для одного пользователя это правильно, для общей
  базы команды — нет. Нужно решить, привязывать ли `user`-факты к `client`/логину.
- **Качество эвристического fallback**: без LLM режим `auto` останется примерно
  нынешним auto-accept `Lesson`; честно показать это в UI («без провайдера отбор
  грубее»).
