# Изоляция памяти между проектами: план и статус

Цель: агент одного проекта не должен видеть и не должен менять память другого
проекта. Это касается и prompt injection: модель не может ни прочитать чужой узел
по id, ни переключить проект, ни переписать чужое знание. Требование относится ко
всем входам: MCP-серверу, хукам агентов, AI-ранам через tool gateway, HTTP с
`project_id` и SDK.

## 1. Правило видимости (чтение)

- Единое правило — `MemoryEmbeddingEngine._passes_scope_filter` / `node_visible`
  (`backend/architectos/embeddings.py`). Его SQL-копия —
  `storage_search.scope_visibility_sql`. Оба правила должны меняться вместе.
- Проекту видны свои узлы, узлы без `project_id` и узлы со scope `shared`/`global`.
  Узлы `project_shared`, `user_private` и `interface` чужого проекта скрыты.
- Явный `scope` в поиске только сужает выдачу по сравнению со `scope=None` и
  никогда её не расширяет.
- Скрытый id неотличим от несуществующего: тот же текст ошибки и тот же
  `hit_count`, у скрытых узлов нет побочных эффектов (событий, lifecycle). Id
  скрытых узлов вырезаются из metadata, истории, хитов, stable- и rule-слоя,
  briefing и graph-ответов. Хранилище при этом не меняется.

## 2. Правило записи (владение)

Решение пользователя: если у записи есть **проект вызывающего**, ничто вне его
владения не меняется. Под запрет попадают SUPERSEDES, enrich, fold, evidence,
confidence, metadata и события чужого узла. Вместо изменения создаётся новый узел
со ссылкой `possible_duplicate_of`. Если активный чужой узел уже содержит тот же
факт, запись получает held и ничего не пишет. Свой узел проект по-прежнему может
заменить, обогатить и оживить. Без проекта вызывающего (несвязанный сервер,
HTTP/UI без проекта, внутренние compaction и dedup) поведение прежнее.

- Владелец: `node.project_id`, а для shared/global — `author_project_id`
  (хранится в payload и в id не входит). Проверка одна:
  `owned_by(node, caller)` (`models.py`). Подробности — в
  `MEMORY_DEDUP_RU.md`, раздел «Владение и проект вызывающего».
- Legacy shared/global-узлы без автора считаются ничьими, то есть чужими для всех
  проектов. Backfill автора не делается.
- `memory_link` SUPERSEDES разрешён только на узел, которым вызывающий владеет.
- Ревизия (`_apply_revision_supersede`) с проектом вызывающего заменяет только
  свой предшественник и помечает `source_stale_at` только свои факты.

## 5. Принятые решения

- AI-ран: модель не может переключить проект. Для `boards_*`/`repo_*` поле
  `project_id` означает проект Azure DevOps, поэтому их это правило не касается.
- Несвязанный MCP-сервер (без проекта) видит всё, как и раньше. Явный
  `project_id` в аргументах MCP переключает проект: это сделано намеренно,
  пользователь сам называет проект.
- Gate действует на каждый вход с проектом: MCP add/bulk/split, авто-запись
  хуков и `capture_memory_turn`, promote, Review Accept и batch, HTTP
  `POST /api/memory`, SDK `add`, Ask-чат. Review Accept берёт проект кандидата.
- Ask-чат без `project_id` пишет в проект по умолчанию `architectos` и выступает
  от его имени.
- `access_count`/`memory_score` общих узлов меняются от чтений всех проектов. Это
  телеметрия, а не мутация gate.
- Ревизия чужого узла с проектом вызывающего ведёт себя как `update` шлюза по
  чужой цели. Предшественник не меняется: нет SUPERSEDES, `invalid_at` и
  `superseded_by`. Новая ревизия получает `possible_duplicate_of` и
  `dedup_suggestion` с действием `update`, в лог пишется WARN. Без проекта
  вызывающего ревизия заменяет предшественника, как раньше.
- Цепочка своих ревизий рядом с чужим предшественником. Чужой узел X остаётся
  живым, поэтому у origin key (и у `fact_subject:`) живых узлов два: X и своя
  ревизия Y. `_origin_indexes` (`memory_ingestion.py`) берёт живой origin из
  узлов, которыми владеет проект ingest (`owned_by`), и только если таких нет —
  чужой или legacy-узел. Поэтому следующая ревизия Z получает `revision_of = Y` и
  заменяет Y как обычно, живой остаётся одна своя ревизия, а X не меняется.
  `possible_duplicate_of` на X получает только первая ревизия, рядом с которой
  своего узла ещё не было. Выбор origin делается при ingest, где проект известен
  всегда, а не при promote. Поэтому он меняет и запись без вызывающего, но только
  когда у одного origin key живы и свой, и чужой узел. Тогда ревизия без
  вызывающего заменяет свой узел, а не чужой.
- HTTP-предпросмотр `POST /api/memory/dedup/preview` с `project_id` считает этот
  проект вызывающим, как `POST /api/memory`, и отвечает тем же решением: held
  (`dedup_held`) или новый узел рядом с чужим (`suggested_action`). Кандидаты
  берутся из индекса по паре (scope, проект), поэтому скрытых узлов другого
  проекта в ответе нет. Без `project_id` предпросмотр прежний.
- `|` внутри частей id узла (`memory_node_id`) заменяется на `\x00`. Части без
  `|` дают прежний id, сам `stable_id` не менялся: id кандидатов, рёбер и других
  сущностей остаются прежними. У существующего узла с `|` в метке или
  `interface_id` при повторной записи id меняется. Если запись идёт через шлюз,
  повтор того же факта находится по индексу и сворачивается в старый узел. Пути
  мимо шлюза перезаписывали узел по id, а теперь кладут копию под новым id. Это
  promote с `interface_id`, `add_memory` с `dedup: false`, прямой
  `repository.add_node`, `_write_candidates_directly_to_memory`,
  `project_scan_service` и `code_graph`. Риск низкий и принят. Копии сводятся
  через Review (Memory › Duplicates) или компактизацию dedup.
- После замены `|` → `\x00` части `a|b` и `a\x00b` в одной позиции дают один id.
  Это алиас внутри одного слота (тот же тип, scope, проект и `interface_id`), а
  не обход владельца: чужой узел в слоте шлюз видит как чужой и солит запись.
  Принято.
- Promote с `interface_id` (`replace_own`) рядом с чужим узлом солится только
  проектом вызывающего: `"<caller>:"`. Повторный promote с изменённым текстом
  переписывает ту же свою копию. Копии, созданные до этой правки под солью
  `"<caller>:<hex>"`, остаются как есть, следующий promote создаст копию
  `"<caller>:"` один раз.

## 6. Открыто (follow-up)

- Ревизии без проекта вызывающего (авто-promote кодовых ревизий и прямая запись
  `_write_candidates_directly_to_memory`) по-прежнему заменяют любого
  предшественника. `revision_of` ищется по origin key (`source_type` +
  `source_ref`) среди узлов проекта и узлов без `project_id`, и свой узел
  выбирается первым. Если своего нет, это может быть shared-узел другого
  проекта. Передавать ли проект ingest как вызывающего — открытый вопрос.
- Ревизия, принятая через promote с `interface_id = rev:<hash>`, идёт мимо
  `_gate_decision` (`ingestion_candidates.py`, около строки 123). Пусть на том
  же origin key есть свой узел O, а атом дословно повторяет активный чужой узел.
  Тогда пишется свой узел без `possible_duplicate_of` и без held. Цепочка своих
  ревизий при этом верная. Риск низкий, только follow-up.
- Мутирующие HTTP-эндпоинты (pin, merge, favorite, promote-long-term) проект
  не проверяют: UI считается доверенным.
- Если авто-запись свернула факт в существующий узел своего проекта,
  `undo_auto_capture` архивирует этот узел. Так было и до изоляции.
- Опциональный backfill автора для legacy-узлов по истории кандидатов.
- Held срабатывает только при совпадении и метки, и текста (exact restatement).
  Если тот же текст пришёл с другой меткой, например голосовая запись без метки
  получает метку из текста, рядом с чужим узлом создаётся новый узел с
  `possible_duplicate_of`.

независимое ревью, полный прогон тестов, а тесты на новое поведение должны падать
на коде до правки.
